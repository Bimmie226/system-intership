# Nova File log

## I. Log dùng để làm gì?

Log ghi nhận hoạt động và lỗi của dịch vụ. Với Nova, cần đọc log để biết yêu cầu đã tới thành phần nào, lỗi xảy ra ở bước chọn host hay tạo VM, và có dịch vụ phụ thuộc nào liên quan.

Trạng thái `ERROR` là điểm bắt đầu điều tra. Trường `fault` cung cấp thông tin ban đầu; log thường chứa ngữ cảnh và traceback chi tiết hơn. Xem [Troubleshoot Compute](https://docs.openstack.org/nova/latest/admin/support-compute.html).

## II. Vị trí và các file log chính

### 2.1. Thư mục thường gặp

| Kiểu triển khai | Đường dẫn trên node chạy dịch vụ |
|---|---|
| Cài bằng package, có ghi log ra file | `/var/log/nova/` |
| Kolla-Ansible | `/var/log/kolla/nova/` |
| Ghi vào journald hoặc stderr | Xem journal hoặc log container theo cấu hình |

Đường dẫn và tên file có thể được tùy chỉnh. Với Kolla, đọc file trên **host** là cách thường dùng để xem log ứng dụng. `docker logs` cung cấp stdout/stderr của container và có thể chỉ hiện thông tin khởi động. Xem [Compute service logging](https://docs.openstack.org/nova/latest/admin/support-compute.html#compute-service-logging) và [Kolla debugging](https://docs.openstack.org/kolla-ansible/latest/user/troubleshooting.html#debugging-kolla).

### 2.2. File log theo dịch vụ

| File thường gặp | Node thường chứa | Nội dung cần tìm |
|---|---|---|
| `nova-api.log` | Controller / API node | Tiếp nhận request, policy, validation và lỗi API |
| `nova-scheduler.log` | Controller / scheduler node | Chọn host, filters, allocation candidates, `NoValidHost` |
| `nova-conductor.log` | Node chạy conductor | Điều phối build/resize, RPC, xử lý dữ liệu và lỗi retry |
| `nova-compute.log` | Compute node | Spawn VM, libvirt, kết nối volume, VIF và migration |
| `nova-novncproxy.log` | Node chạy noVNC proxy | Console token và kết nối tới VNC server |
| `nova-serialproxy.log` | Node chạy serial proxy, nếu bật | Kết nối serial console |

API chạy dưới web server có thể có thêm access/error log riêng. Metadata API cũng có thể ghi vào file riêng tùy cách đóng gói. Xem cấu hình logging hoặc danh sách file thực tế khi tên file khác bảng trên.

## III. Cách đọc một dòng log

Ví dụ minh họa, không phải log thu từ lab:

```text
2026-11-25 10:15:20.123 1234 ERROR nova.compute.manager [req-<UUID> ...] [instance: <INSTANCE_UUID>] Failed to build instance
```

| Thành phần | Ý nghĩa |
|---|---|
| Timestamp | Thời điểm ghi log; kiểm tra múi giờ khi đối chiếu giữa các node |
| PID | Mã tiến trình ghi log |
| Level | Mức độ: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` |
| Logger | Module phát sinh thông điệp, ví dụ `nova.compute.manager` |
| Request ID | Mã định danh để lần theo một yêu cầu |
| Instance UUID | Mã instance liên quan |
| Message / traceback | Nội dung và chi tiết exception |

Nova sử dụng `oslo.log`; định dạng thực tế phụ thuộc cấu hình. `INFO` mô tả hoạt động thông thường, `WARNING` cần chú ý, còn `ERROR` thường đi kèm lỗi xử lý. Xem [oslo.log configuration](https://docs.openstack.org/oslo.log/latest/configuration/index.html).

**Request ID có phạm vi:** local request ID có thể khác giữa Nova, Neutron, Cinder và Glance. Global request ID hỗ trợ liên kết giữa các dịch vụ khi được truyền đi. Nếu tìm một ID không ra kết quả, đối chiếu thêm UUID, thời gian và lời gọi dịch vụ liên quan. Xem [Tracking Errors by Request ID](https://docs.openstack.org/api-guide/compute/faults.html#tracking-errors-by-request-id).

## IV. Lệnh xem log cơ bản

Các ví dụ dùng terminal Linux trên node OpenStack. Với triển khai bằng package, thay `/var/log/kolla/nova` bằng thư mục log thực tế.

```bash
# Xem các file hiện có
sudo ls -lh /var/log/kolla/nova/

# Đọc 100 dòng cuối trên compute node
sudo tail -n 100 /var/log/kolla/nova/nova-compute.log

# Theo dõi khi tái hiện lỗi
sudo tail -F /var/log/kolla/nova/nova-compute.log

# Tìm lỗi, giữ thêm các dòng sau để đọc traceback
sudo grep -n -A 20 -E 'ERROR|CRITICAL|Traceback' \
  /var/log/kolla/nova/nova-compute.log

# Tìm theo instance UUID hoặc request ID
sudo grep -n -F '<INSTANCE_UUID>' /var/log/kolla/nova/nova-compute.log
sudo grep -n -F 'req-<UUID>' /var/log/kolla/nova/nova-conductor.log
```

Khi log đã rotate, cần tìm cả file cũ. Dùng `zgrep` với file nén đã xác định:

```bash
sudo zgrep -n -F '<INSTANCE_UUID>' /var/log/kolla/nova/nova-compute.log.1.gz
```

Kiểm tra stdout/stderr nếu container không khởi động được:

```bash
sudo docker ps -a
sudo docker logs --tail 100 nova_compute
```

Với dịch vụ chạy bằng systemd và ghi journal, xác định đúng tên unit của distro trước:

```bash
systemctl list-units --all '*nova*'
sudo journalctl -u <NOVA_COMPUTE_UNIT> --since '30 minutes ago'
```

## V. Quy trình đọc log khi VM lỗi

### 5.1. Lấy thông tin instance và event

Chạy trên máy có OpenStackClient và credentials phù hợp:

```bash
openstack server show <VM_NAME_OR_UUID>
openstack server event list <VM_NAME_OR_UUID>
openstack server event show <VM_NAME_OR_UUID> <REQUEST_ID>
```

Ghi lại UUID, thời điểm thao tác, `fault`, `status`, `task_state` và compute host nếu đã được gán. Một số chi tiết event hoặc host cần quyền quản trị. API có thể tiếp nhận yêu cầu thành công nhưng tác vụ phía sau thất bại. Xem [Compute API — Faults](https://docs.openstack.org/api-guide/compute/faults.html).

### 5.2. Chọn log theo giai đoạn gặp lỗi

| Triệu chứng | Điểm bắt đầu kiểm tra |
|---|---|
| API trả `401` / `403` | Credentials, scope, policy; log API / Keystone khi cần |
| `NoValidHost` | Scheduler, yêu cầu flavor/traits, Placement và trạng thái compute |
| Build thất bại sau khi chọn host | Conductor và compute được chọn; kiểm tra thêm các host retry nếu có |
| Lỗi gắn volume | Compute, Cinder và đường kết nối storage |
| `Binding failed for port` | Compute, Neutron server và backend mạng tương ứng |
| Console không kết nối | noVNC proxy, mạng tới compute và VNC server |
| Migration lỗi | Conductor, compute nguồn và compute đích |

Đọc các dòng trước exception cuối cùng để tìm lỗi khởi phát. Thông báo như `Exceeded maximum number of retries` thường chỉ là kết quả cuối của các lần build thất bại. Hướng kiểm tra compute và hypervisor được mô tả trong [Troubleshoot Compute](https://docs.openstack.org/nova/latest/admin/support-compute.html).

### 5.3. Ví dụ lần theo lỗi build trên Kolla

```bash
# Trên controller / node chạy conductor
sudo grep -n -F '<INSTANCE_UUID>' /var/log/kolla/nova/nova-conductor.log

# Trên từng compute liên quan
sudo grep -n -F '<INSTANCE_UUID>' /var/log/kolla/nova/nova-compute.log
```

Nếu log compute chỉ tới lỗi Cinder hoặc Neutron, tiếp tục sang log dịch vụ đó với cùng khoảng thời gian và định danh liên quan. Cần xác minh nguyên nhân trước khi thay đổi trạng thái hoặc restart dịch vụ.

## VI. Log liên quan ngoài Nova

| Nguồn | Dùng khi nào? |
|---|---|
| QEMU / libvirt | VM không khởi chạy hoặc hypervisor báo lỗi; QEMU log thường ở `/var/log/libvirt/qemu/` trong môi trường libvirt |
| Neutron | Lỗi port binding, VIF, agent hoặc kết nối mạng |
| Cinder / os-brick | Lỗi attach volume, iSCSI, multipath hoặc backend storage |
| Placement | Lỗi truy vấn tài nguyên hoặc allocation |
| RabbitMQ | Lỗi AMQP, RPC timeout hoặc mất kết nối broker |
| Guest console | Kernel boot, lỗi hệ điều hành hoặc output cloud-init đã gửi ra console |

Với Kolla, tìm thư mục tương ứng dưới `/var/log/kolla/`; đường dẫn libvirt cụ thể phụ thuộc container và volume mount. Xem [Kolla debugging](https://docs.openstack.org/kolla-ansible/latest/user/troubleshooting.html#debugging-kolla).

Với libvirt và thư mục instance mặc định, text console thường nằm tại `/var/lib/nova/instances/<INSTANCE_UUID>/console.log` trong môi trường compute. Có thể lấy output qua API để không cần truy cập trực tiếp file:

```bash
openstack console log show <VM_NAME_OR_UUID>
```

Đây là output console của guest, khác log `nova-compute` và phiên console đồ họa noVNC. Xem [OpenStackClient — console log show](https://docs.openstack.org/python-openstackclient/latest/cli/command-objects/compute/v2/index.html#console-log-show).

Nếu đăng nhập được guest có cloud-init, xem thêm `/var/log/cloud-init.log` và `/var/log/cloud-init-output.log` để điều tra quá trình cấu hình bên trong VM. Xem [Cloud-init — Log files](https://docs.cloud-init.io/en/latest/reference/user_files.html).

## VII. Cấu hình logging cơ bản

Với dịch vụ đọc `/etc/nova/nova.conf`, các tùy chọn cơ bản nằm ở `[DEFAULT]`:

```ini
[DEFAULT]
debug = false
log_dir = /var/log/nova
```

`log_file` chỉ định file đích của tiến trình. Khi cả `log_file` và `log_dir` không đặt, đầu ra mặc định đi tới stderr theo cấu hình `use_stderr`. Nếu sử dụng `log_config_append`, file logging riêng điều khiển các handler và có thể thay thế tác dụng của các tùy chọn trên. Xem [oslo.log configuration](https://docs.openstack.org/oslo.log/latest/configuration/index.html).

Với Kolla, ví dụ bật DEBUG cho compute bằng override trên deploy node:

```ini
# /etc/kolla/config/nova/nova-compute.conf
[DEFAULT]
debug = true
```

Áp dụng bằng inventory thực tế:

```bash
kolla-ansible -i <INVENTORY_PATH> reconfigure --tags nova
```

Kolla có thể tạo lại cấu hình trong container; cần lưu tùy chỉnh tại override và kiểm tra cấu hình đã render sau reconfigure. Xem [Kolla — OpenStack service configuration](https://docs.openstack.org/kolla-ansible/latest/admin/advanced-configuration.html#openstack-service-configuration-in-kolla).

Chỉ bật DEBUG trong thời gian điều tra, sau đó đặt lại `debug = false` và áp dụng lại. Khi chia sẻ log, che token, mật khẩu, URL console chứa token và dữ liệu nhạy cảm xuất hiện trong output.
